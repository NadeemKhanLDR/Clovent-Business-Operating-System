## B. Business Rules

### 1. Item Addition & Variant Naming
- **Single Variant Products:** Clicking a menu item adds 1x Standard portion variant to the cart.
- **Multi-Variant Products (Full / Half):** Each variant displays as `[Product Name] - [Portion]` (e.g. `Aloo Gobi - Full`, `Aloo Gobi - Half`).
- **Naming Consistency:** The `Product Name - Portion` naming format is used consistently across Cart, Hold, Recall, Active Orders, Receipts, Payment History, and Sales History.
- **Portion Normalization:** "Regular" or default portions render as `Product Name` without redundant portion suffixes.

### 2. Duplicate Item Behavior
- **Same Item + Same Variant + No Notes:** Merges into a single line with incremented quantity (`Quantity = Quantity + addedQty`).
- **Same Item + Same Variant + Custom Notes:** Maintained as separate lines to ensure distinct kitchen modifiers (e.g., `Note: Less spicy` vs. `Note: Extra spicy`) do not overwrite one another.

### 3. Quantity Controls
- **Validation:** Quantity must be a positive integer ($\ge 1$).
- **Controls:** `+` (increment), `-` (decrement), and `Qty` button / inline cell editor.
- **Immediate Recalculation:** Changing quantity immediately recalculates Subtotal, Tax, Discount, Service Charge, Total Payable, and Balance Due across all UI controls and domain models.

### 4. Notes Persistence
- **Item Notes (`OrderLine.Notes`):** Attached per cart line. Persisted in database and preserved across `MENU -> CART -> HOLD -> RECALL -> CART -> COMPLETE`.
- **Order Notes (`Order.Notes`):** Free-text internal notes attached to the order.
- **Customer Notes (`Order.CustomerNotes`):** Customer-facing notes printed on receipts.

### 5. Delete vs. Void Semantics
- **Delete (`RemoveOrderLineCommand`):** Removes uncommitted lines from an active working order before payment/kitchen processing.
- **Void (`VoidOrderLineCommand` / `VoidOrderCommand`):** Audit operation. Sets `IsVoided = true`. Voided lines and orders are excluded from financial totals and kitchen tickets but preserved permanently in the database for audit trails.
- **Manager Authorization:** Full order voiding requires reason prompt and Manager Authorization (`pos.void` permission).

### 6. Price Override
- **Catalog Snapshot:** `OriginalUnitPrice` preserves the catalog price at creation.
- **Price Edit (`OverrideOrderLinePriceCommand`):** Authorized via `pos.priceoverride` permission (button or inline grid editor). Requires a reason and records the cashier/manager user.
- **Persistence:** Overridden prices persist through Hold, Recall, Receipt printing, and Sales History.

### 7. Authoritative Total Calculation
All money totals are computed by `OrderTotalsCalculator` via a single, authoritative path:
$$\text{Subtotal} = \sum (\text{Quantity} \times \text{UnitPrice} \quad \forall \text{ active lines})$$
$$\text{Grand Total} = \text{Subtotal} - \text{DiscountTotal} + \text{ServiceChargeTotal} + \text{ExclusiveTaxTotal}$$
$$\text{Balance Due} = \text{Grand Total} - \text{PaidTotal}$$

### 8. Balance Due Behavior
- **Dynamic Balance:** `Balance Due` equals `Grand Total` minus `PaidTotal` (non-voided payments).
- **Partial Payments:** Subtotal and Grand Total remain fixed while Balance Due decreases as partial payments are recorded.

### 9. Hold & Recall Integration
- **Hold Order (`HoldOrderCommand`):** Transitions order status to `Held`. Preserves order ID, number, items, variants, quantities, notes, prices, customer, and table. Clears the working cart UI safely without deleting persisted orders.
- **Recall Order (`RecallOrderDialog`):** Restores held orders back into the POS workspace with 100% data fidelity.
- **Safety Checks:** Switching orders or recalling a held order when active unsaved edits exist prompts the cashier to hold the current order first.

### 10. Clear Working Cart
- **Clear Action (`ClearOrderAsync`):** Safely resets the UI workspace (`_currentOrder = null`, `_currentOrderLines = []`) without deleting or cancelling held or open orders in the database.

### 11. Dine In vs. Take Away
- **Dine In:** Requires a valid table (`TableId`). Table selector control is enabled.
- **Take Away:** `TableId` is `null`. Table selector control is disabled and unselected.

### 12. Customer & Table Association
- **Customer Association:** Defaults to Walk-in Customer (`CustomerId = null`). Selecting a customer associates them with `Order.CustomerId` and displays outstanding balance.
- **Table Association:** Occupied tables link to `Order.TableId` and update occupancy status on the table map. Vacated when order is completed or voided.

## C. Order Lifecycle Workflow

$$\text{NEW} \longrightarrow \text{ADD ITEMS} \longrightarrow \text{MODIFY CART} \longrightarrow \text{HOLD} \longrightarrow \text{CLEAR UI} \longrightarrow \text{RECALL} \longrightarrow \text{RECORD PAYMENT} \longrightarrow \text{COMPLETE}$$

- **Open:** Active order receiving item additions or modifications.
- **Held:** Persisted in database, available for recall.
- **Completed:** Fully paid ($\text{Balance} \le 0.005$), inventory stock issued, table vacated.
- **Voided:** Discarded with audit reason and manager authorization.
- **Cancelled:** Cancelled before any payment has been recorded.

## D. Technical Implementation

### Key Components Changed/Hardened
1. **`RestaurantPosForm.cs`**:
   - Central POS desktop form.
   - Dual grid/list menu viewports with responsive layout engine (1024x768 and 1366x768).
   - In-place grid editing for Quantity and Price with permission gates.
   - Active Orders collapsible rail with status filters (`Active Orders`, `Take Away`, `Closed`, `Wait List`).
   - Integrated tender strip, keypad, quick cash, and action buttons.
2. **`OrderTotalsCalculator.cs`**:
   - Pure domain calculation engine for Subtotal, Tax, Discount, Service Charge, Grand Total, Paid Total, and Balance.
3. **`Order.cs` & `OrderLine.cs`**:
   - Aggregate roots managing order transitions and line item immutability/overrides.
4. **`RecallOrderDialog.cs`**:
   - Browse and recall held/open orders with search, preview, and stale-data re-query guards.

## F. Technical Debt

- **DailySalesSequence Concurrency:** Per-day, per-warehouse sequential invoice numbers intentionally increment on completed sales. High-concurrency multi-terminal locking is documented active technical debt and preserved without regression.
- **Menu Item Image Store:** Photos stored as local files in `%LocalAppData%` rather than database binary blobs.
- **Cash/Card Substring Reporting:** End-of-Day report categorizes Cash vs. Card via substring checks on payment method name.
- **N+1 Entity Queries:** UI tile and summary renderers query prices and metadata in sequential loops.
