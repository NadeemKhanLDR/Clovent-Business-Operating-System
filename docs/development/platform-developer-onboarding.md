## 1. System Architecture & Solution Map

The Clovent Business Operating System is structured as a clean-architecture **Modular Monolith** targeting .NET 10. Each bounded context is isolated into layered assemblies:

```
src/
├── Clovent.Domain/                     # Enterprise shared domain primitives (AggregateRoot, EntityId)
├── Clovent.Platform/                   # Host execution, circuit breakers, configuration, printing abstractions
├── Clovent.Authentication/             # Password hashing, tokens, credentials domain & EF schema
├── Clovent.Identity/                   # Organizations, Companies, Branches, Users, Roles, RBAC
├── Clovent.MasterData/                 # Currencies, Warehouses, Terminals, FiscalYears, Settings
├── Clovent.Catalog/                    # Products, Categories, Variants, Prices
├── Clovent.Inventory/                  # Stock items, Warehouse inventory records
├── Clovent.Restaurant/                 # Hospitality POS domain (Orders, Tables, Shifts, Payments, Snapshots)
├── Clovent.Restaurant.Application/     # Commands, Queries, Totals, Printing, Continuity replay
├── Clovent.Restaurant.Infrastructure/  # EF Core DbContext, Outbox processor, DPAPI journals
└── Clovent.Desktop/                   # WinForms + DevExpress 26.1 Client Application
```

### Dependency Rules:
1. **Domain Layer:** Pure C#. Zero dependencies on outer layers, EF Core, or presentation packages.
2. **Application Layer:** References Domain. Contains MediatR commands, queries, DTOs, and interfaces.
3. **Infrastructure Layer:** Implements persistence, external adapters, Outbox processing, and database migrations.
4. **Desktop Layer:** WinForms UI. Binds to Application layer via MediatR and dependency injection.

## 2. Safe Local Development & Synthetic Data Invariants

1. **Test Data Privacy Invariant:**
   - **Never** commit, log, or use real customer business data, customer phone numbers, tax IDs, or actual payment card details.
   - Always use synthetic fixtures generated by test generators or standard development seeds.
2. **Workstation State Isolation:**
   - Automated tests must run in isolated temporary directories or SQLite in-memory databases.
   - Tests must **never touch** production `%ProgramData%\Clovent\BusinessOperatingSystem\` folders, developer operational SQL Server instances, or registry keys.
3. **Safe Startup with Synthetic Data:**
   - When running locally in `Debug` configuration, development seed tasks (`DevelopmentUserSeedStartupTask`) populate synthetic accounts, categories, and items.
   - In production builds (`#if !DEBUG`), developer seed tasks are physically disabled.

## 3. How to Implement Common Platform Extensions

### 3.1 Adding a New Feature or Use Case
1. **Define Domain Aggregate / Entity:** Place in `src/Clovent.<Context>/<Feature>/`.
2. **Define MediatR Command / Query:** Place in `src/Clovent.<Context>.Application/<Feature>/Commands/` or `Queries/`.
3. **Implement Handler:** Enforce business invariants. Return immutable DTOs, never domain entity references.
4. **Persistence Mapping:** Add EF Core entity configuration in `src/Clovent.<Context>.Infrastructure/Persistence/Configurations/`.
5. **Unit Tests:** Add unit tests covering command validation, domain events, and boundary edge cases in `src/Clovent.<Context>.Application.Tests/`.

### 3.2 Adding a New Hardware / Printer Adapter
1. **Implement `IPrinterAdapter`:**
   - Located in `src/Clovent.Platform/Printing/IPrinterAdapter.cs` or `src/Clovent.Desktop/Printing/`.
   - Provide `SupportedConnection` flag (e.g. `WindowsDriver`, `EscPosNetwork`).
   - Implement `DispatchAsync(PrinterProfile profile, PrinterJob job, CancellationToken ct)`.
2. **Handle Failure Gracefully:**
   - Return structured `PrintDispatchResult` with explicit `JobStatus`.
   - **Never roll back a completed financial transaction** upon printer communication failure.
3. **Register Adapter in DI Container:**
   - Register implementation in `PrinterManagementService` or `PlatformServiceCollectionExtensions`.

### 3.3 Adding an External System Integration
1. **Define Provider Interface:** Small, focused contract in Application layer.
2. **Use the Transactional Outbox Pattern:**
   - Operational commands enqueue an `OutboxMessage` in the same atomic database transaction.
   - Background `OutboxProcessor` polls and dispatches via typed message handler.
3. **Enforce Circuit Breaker & Retry:**
   - Wrap network I/O in `ICircuitBreakerRegistry.GetOrCreate("ProviderName")`.
   - Apply exponential backoff. Transition failed messages to DeadLetter with raw payload intact.

## 4. Persistence & Migration Ownership Rules

1. **One Physical Database:**
   - Single database: `Clovent_BusinessOperatingSystem`.
   - Each bounded context operates a dedicated schema: `[Authentication]`, `[Identity]`, `[MasterData]`, `[Catalog]`, `[Inventory]`, `[Restaurant]`.
2. **Isolated Migration History:**
   - Each context maintains its own migration history table: `__EFMigrationsHistory_Identity`, `__EFMigrationsHistory_Restaurant`, etc.
   - Never share migration history across contexts.
3. **Frozen Release Invariant:**
   - **CBOS 1.2.3 Pilot Baseline:** Strictly **ZERO DATABASE MIGRATIONS**. All 1.2.3 capabilities must use existing tables and columns.
   - Additive migrations are strictly scheduled for CBOS 1.3.0 and subsequent releases.

## 5. UI & High-DPI Guidelines (WinForms & DevExpress 26.1)

1. **Designer Safety:**
   - Every Form and UserControl must provide a parameterless or designer-safe constructor.
   - Always guard form loading: `if (DesignModeHelper.IsInDesignMode) return;`.
   - Do not invoke MediatR, service locators, or filesystem operations in `InitializeComponent()`.
2. **High-DPI PerMonitorV2:**
   - `AutoScaleMode = AutoScaleMode.None;` is standard for DevExpress DPI-aware containers.
   - Use `DesktopDpi.Scale(value, this)` for dynamic bounds and minimum size constraints.
   - Test at standard 96 DPI (100%) and high-density 240 DPI (250%) scaling at 1920×1080.
3. **Touch-Friendly Controls:**
   - Minimum editor height: 32px.
   - Minimum action button height: 40px to 48px.

## 6. Build, Testing & Quality Assurance Protocol

### Standard Build Commands:
- Debug Build: `dotnet build Clovent.BusinessOperatingSystem.slnx -c Debug`
- Release Build: `dotnet build Clovent.BusinessOperatingSystem.slnx -c Release`

### Running Tests:
- Run targeted tests for your modified assembly:
  ```powershell
  dotnet test src/Clovent.Platform.Tests/Clovent.Platform.Tests.csproj
  dotnet test src/Clovent.Desktop.Tests/Clovent.Desktop.Tests.csproj
  ```
- Do not poll running test processes in a loop. Await the execution result.
