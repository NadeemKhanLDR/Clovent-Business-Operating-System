# Desktop UI Layout Standard

This document is the layout/spacing/typography standard for every screen in `Clovent.Desktop`, and the record of a responsive-layout audit and fix pass triggered by a visibly broken Dashboard (overlapping labels, merged text, misaligned KPI cards, controls that didn't resize with the window). It complements `DesktopShellArchitecture.md` (shell/document/`BaseForm` architecture) and `DesktopBootstrap.md` (project history) - this document owns *layout* standards specifically.

---

## 1. The rule: no hardcoded pixel positioning

**A control's position and size must come from `Dock`, `Anchor`, `TableLayoutPanel`, or `FlowLayoutPanel` - never from a bare `Location = new Point(x, y)` relying on default anchoring.** Default `Anchor` is `Top, Left` - a control placed this way never moves or resizes when its container does, which is exactly what produced Dashboard's bug: fields overlapped because the window was a different size than the exact pixel canvas the coordinates were authored against, and a value label's fixed `Size(15, 50)` clipped any real value to nothing.

This does not mean literal coordinates never appear - `TableLayoutPanel`/`FlowLayoutPanel` rows/columns are still frequently given `Absolute` sizes (e.g. a toolbar row's height, a KPI card's height) where a *fixed, readable* size is actually wanted. The distinction: an `Absolute` `RowStyle`/`ColumnStyle` size is a deliberate, contained sizing decision for one dimension of a layout container; a bare `Control.Location`/`Control.Size` with default `Anchor` is an uncontained pixel position that silently breaks the moment the window doesn't match the exact canvas it was authored at.

## 2. Spacing/padding/margin standard

Defined once in `Forms/Base/DesktopStyle.cs` and referenced from every screen's `.Designer.cs` rather than re-picked per screen:

| Constant | Value | Use |
|---|---|---|
| `ControlGap` | 8px | Gap between adjacent toolbar controls (used as `FlowLayoutPanel` child `Margin`). |
| `PanelPadding` | 8px | Outer padding for a panel/section. |
| `ToolbarHeight` | 44px | Starting toolbar band height (live-adjusted by `BaseForm.ToolbarFlow`'s `SizeChanged`, see Section 5). |
| `ToolbarControlHeight` | 30px | Height for a toolbar `SimpleButton`/`TextEdit`. |
| `ButtonWidthSmall` / `Medium` / `Large` | 80 / 100 / 130px | Standard button widths ("New"/"Edit"/"Refresh" vs. "Activate"/"Export CSV" vs. "Reset Password"). |
| `SearchBoxWidth` | 220px | Standard toolbar search box width. |
| `CardGap` | 12px | Gap between KPI/summary cards (`Margin` on each card). |
| `CardHeight` | 110px | Standard KPI card height. |
| `PageTitleFont` | Segoe UI 18pt Bold | Screen title ("Dashboard", "Welcome back"). |
| `SectionHeadingFont` | Segoe UI 11pt Bold | Section captions ("Recent Activity", context values). |
| `CardValueFont` | Segoe UI 20pt Bold | KPI card's big number. |
| `CaptionFont` | Segoe UI 9pt | Field/status captions. |
| `CaptionForeColor` | `Color.Gray` | Muted secondary caption color. |

Every screen this pass touched (Dashboard, Login, Users, Roles, Products, and the three Designer-split edit dialogs) references these instead of re-choosing sizes/fonts, which is what "every screen looks like it belongs to the same ERP" (Section 11 of the request) actually means in code - a shared constants class, not a per-screen guess.

## 3. Toolbar standard

Every `BaseForm`-derived screen gets an identical toolbar mechanism for free (see Section 5): a `FlowLayoutPanel` (`ToolbarFlow`) inside the inherited `ToolbarPanel`, `WrapContents = true`, `AutoSize` + `AutoSizeMode.GrowAndShrink`, height driven live by the flow's own `SizeChanged`. A screen's own `.Designer.cs` only ever adds controls to `ToolbarFlow.Controls`, in left-to-right order, each with an explicit `Size` (from the table above) and a `Margin` for spacing - never a `Location`. This is the exact pattern `MasterData/MasterDataListView.cs`'s toolbar already proved (including two real historical bugs it fixed: a fixed height too short for a button's real rendered height under some DPI/skin combос, and an overflowing button row with no way to reach the clipped buttons - `WrapContents=true` solves the second one by wrapping to a second row instead).

**Standard toolbar button order**: search box, then New, Edit, then status-changing actions (Activate/Deactivate), then entity-specific extras (Reset Password, Unlock, Export/Import CSV), then Refresh last.

## 4. Common form layout (list/management screens)

**Superseded by Session 4 (Section 8b).** Every business form - whether built on the shared `MasterData.MasterDataListView<TDto>` framework (~30 screens) or hand-authored as a `BaseForm` (Users/Roles/Products) - now follows a left command panel + grid shape instead of a toolbar-above-grid strip:

```
BaseForm (or MasterDataListView<TDto>)
  ContentPanel (Dock=Fill)
    SplitContainer (Dock=Fill, FixedPanel=Panel1)
      Panel1 (fixed ~240px)  -> command panel: Search / Actions / Info sections,
                                 a FlowLayoutPanel (TopDown), built via
                                 Forms.Base.CommandPanelLayout (or, for
                                 MasterDataListView specifically, its own
                                 earlier-verified inline equivalent)
      Panel2 (grows)         -> GridControl, Dock=Fill
```

`ToolbarPanel`/`ToolbarFlow` (`BaseForm`'s inherited horizontal toolbar band) still exists for any screen that genuinely wants a top toolbar, but Users/Roles/Products/MasterDataListView no longer use it - it now sits empty for those screens, and `BaseForm.UpdateToolbarPanelSize` collapses it to zero height automatically when empty (Section 8b) rather than reserving dead space for it.

No separate "filter panel" row exists today (none of the current screens need one beyond the command panel's search box) - if a future screen needs one, it goes in the command panel's `FlowLayoutPanel` as its own section (`CommandPanelLayout.BuildSectionHeading("Filters")` + controls), following the same pattern as Search/Actions.

## 5. `BaseForm` responsibilities

`Forms/Base/BaseForm.cs`/`.Designer.cs` - the base class every document-hosted business screen inherits (see `DesktopShellArchitecture.md` Section 5 for the full architectural rationale). This pass added:

- **`ToolbarFlow`** (`FlowLayoutPanel`, replacing a bare `ToolbarPanel` subclasses used to hand-place buttons into): self-wrapping, self-sizing toolbar - the single highest-leverage fix in this pass, since it fixed Users/Roles/Products' toolbars (which had regressed to fixed-pixel/no-`Anchor` positioning) at the framework level, for every current and future `BaseForm` screen at once.
- **Busy-overlay centering**: `BusyOverlayPanel.Resize` recomputes `BusyProgressBar`/`BusyStatusLabel`'s `Location` to stay centered - `Anchor = AnchorStyles.None` (which the overlay still uses) means "don't track any edge," not "stay centered," a common WinForms misconception; genuine centering needs a resize-driven recompute, now provided.
- **`DesktopStyle`** (`Forms/Base/DesktopStyle.cs`): the shared constants from Section 2.
- **No `AutoScaleMode`/`AutoScaleDimensions` anywhere** - this was tried during this pass (to match genuine VS Designer codegen) and reverted after it corrupted every literal coordinate in `DashboardView.Designer.cs` and `ProductsForm.Designer.cs` the moment either was opened in the Designer on a 250%-scaled display (KPI cards collapsed to 1px tall, a toolbar ballooned to 1400+px). See Section 9, guideline 5.

Unchanged responsibilities (from the shell architecture pass): `PermissionKey`, `IsDirty`/`StatusText` + their changed events, `SaveAsync`/`RefreshAsync`/`ConfirmClose` virtuals, `SetBusy`/`RunBusyAsync`.

## 6. Dashboard standard

`Forms/Dashboard/DashboardView.Designer.cs` is built around one outer `TableLayoutPanel` (`tlpMain`, single column, 5 rows - each a different row index, never competing `Dock` siblings, so there is no add-order ambiguity anywhere in the file), hosted inside a plain `System.Windows.Forms.Panel` (`scrollHost`, `AutoScroll=true`) rather than directly in `ContentPanel` - see Section 8b for why:

| Row | Content | Row sizing |
|---|---|---|
| 0 | Title + inline loading bar (`Anchor = Top,Right` - a real anchor, since it only needs to track one edge) | `Absolute 110F` |
| 1 | Current Context strip (Organization/Company/Branch/Fiscal Year/Current User) - a 5-column, 2-row `TableLayoutPanel`, every caption/value `Dock=Fill` within its own cell (replacing the old fixed `Size(15, 50)` value labels that clipped any real value to nothing) | `AutoSize` |
| 2 | KPI card grid - 4 columns x 3 rows, each card `Dock=Fill` with `Margin=CardGap`, each card's own caption (`Dock=Top`) + big value (`Dock=Fill`, centered) | `Absolute`, `3 * (CardHeight + CardGap)` |
| 3 | Recent Activity / Notifications / Stock Movements / Top Selling Items - 4 equal columns, each `Dock=Fill`, absorbing all remaining vertical space | `Percent 100` |
| 4 | Bottom toolbar (Company/Branch selectors + Refresh + View All Notifications) - a `FlowLayoutPanel` | `AutoSize` |

This is the reference example for "how a dashboard-shaped screen should be built" - every future KPI/summary screen should follow the same `TableLayoutPanel`-of-rows-of-`TableLayoutPanel`s-or-`FlowLayoutPanel`s shape rather than inventing a new one. Session 4 (Section 8b) added `pnlTitleBar`/`tlpContext`/`tlpKpi` bottom `Margin`s (8px) for visual separation between sections, and - critically - `BaseForm`'s inherited (but here entirely unused) `ToolbarPanel` no longer reserves a large empty band above the title: see `BaseForm.UpdateToolbarPanelSize`.

## 7. Grid standard

Every `GridControl` in the project: `Dock = DockStyle.Fill`, `OptionsBehavior.AutoPopulateColumns = false` with explicit `GridColumn`s (never letting the grid auto-generate columns from a DTO's every public property), `OptionsView.ColumnAutoWidth = true`, `OptionsView.ShowGroupPanel = false`, `OptionsBehavior.Editable = false` (edits happen through the paired modal dialog, never inline). Confirmed already true for every `GridControl` in the project (`MasterDataListView<TDto>`'s shared grid, and Users/Roles/Products' own hand-authored ones) - no changes were needed here.

## 8. What was audited, what was fixed, what needed no change

A full audit (three parallel searches across every screen category) found the responsive-layout bug is **not** universal - it is concentrated in exactly the screens hand-built with literal pixel coordinates and no `Anchor`. See `DesktopShellArchitecture.md` Section 9 for the complete screen inventory; the layout-specific verdict:

**Fixed this pass:**
- `Forms/Dashboard/DashboardView.Designer.cs` - full redesign (Section 6).
- `Forms/Identity/LoginForm.Designer.cs` - converted from ~15 unanchored fixed-position fields to a `TableLayoutPanel`-based, vertically-centering layout (the project docs had claimed this was already responsive via "TableLayoutPanel + LayoutControl" - that claim did not match the actual code; it's accurate now).
- `Forms/Base/BaseForm` - `ToolbarFlow`, busy-overlay centering, `DesktopStyle` (Section 5).
- `Forms/Identity/Users/UsersForm.Designer.cs`, `Forms/Identity/Roles/RolesForm.Designer.cs`, `Forms/Catalog/Products/ProductsForm.Designer.cs` - toolbar buttons migrated from fixed `Location`/no-`Anchor` into `ToolbarFlow`.
- `MasterData/OrganizationHierarchySelector.cs` - fixed `Height=32` → `AutoSize`, matching the same DPI-clipping fix already applied to its sibling `EntityPicker`/`MasterDataListView`'s toolbar.
- `Forms/Identity/Roles/RoleEditForm`, `Forms/Identity/Users/UserEditForm`, `Forms/Catalog/Products/ProductEditForm` - given a genuine `.Designer.cs`/`.resx` split (fields + `AddField` calls moved into `InitializeComponent()`), and `RoleEditForm.cs`'s stray, broken, uncalled empty `InitializeComponent()` (left behind by Visual Studio auto-generating a stub when its Designer view was opened against a class with no Designer partial) was removed.

**Confirmed already compliant - no changes made:** `MasterData/MasterDataListView.cs`, `MasterData/EntityPicker.cs`, every other `*ManagementView.cs`/`*CreateForm.cs` in MasterData/Catalog/Inventory, every Restaurant/POS screen and dialog (`RestaurantPosView` and its seven dialogs, `TextPromptForm`/`SelectionPromptForm`), `Restaurant/EndOfDay/EndOfDayReportView.cs`, `MasterData/Settings/BusinessSettingsManagementView.cs`, `Identity/Users/PasswordPromptForm.cs`, `Notifications/NotificationsForm.cs`, `Startup/ErrorDialogForm.cs`, and `Forms/Shell/MainForm`'s Ribbon/status bar/`DocumentManager`/`TabbedView` (all DevExpress-framework-managed, not hand-positioned). `MasterDataEditFormBase.cs`'s own claim of compliance here ("its 260px-fixed editor width is moot since these dialogs are FixedDialog/non-maximizable") turned out to be **wrong** - see Section 8a.

**Not addressed by this pass (tracked separately):** the ~114-screen Designer-split backlog from `DesktopShellArchitecture.md` Section 9 (MasterData/Catalog/Inventory/Restaurant screens still on the shared runtime-constructed - but already responsive - framework). Those screens have no layout bug; converting them to hand-authored per-screen Designer forms is a separate completionist goal, not a fix for anything reported here.

**Verification/cleanup pass (session 2):** built the solution end-to-end (it was left mid-refactor, uncommitted, from the pass described above - never actually verified to compile), fixed 6 stale-reference compiler warnings left behind by the `Forms/` move, deleted the five orphan `.Designer.cs`-less `.resx` stub files this document previously left "unaddressed", and ran the full solution test suite (1,291 tests, 0 failures). **This pass only re-read the Designer.cs source and pattern-matched it against the standard above - it never actually ran the application.** That gap mattered: session 3 (Section 8a) found four real, visible overlap/clipping bugs this pass's static review missed entirely, including one (Section 8a's dialog-sizing bug) in a class this pass explicitly certified as "already compliant."

## 8a. Session 3: live-screenshot verification found real bugs static review missed

The user reported the Login and Dashboard screens still visibly overlapped after session 2's pass. Investigation confirmed the report was right: session 2 had verified every screen by reading Designer.cs source and checking it matched the documented pattern (`Dock`/`Anchor`/`TableLayoutPanel` present, no bare `Location`), but never actually launched the app - and a control can follow every rule in Section 1-7 and still overflow its own container if its own literal `Size` doesn't actually fit what it holds, or if the active DevExpress skin renders it larger than whatever pixel number was hand-typed for it. Both turned out to be real, and neither is visible from source alone.

This session added a live-verification capability (PowerShell + `user32`/`gdi32` P/Invoke to launch the built exe, screenshot specific windows, and click-drive navigation - see the session transcript for the exact scripts) and used it to actually render every screen this pass touched, at both default size and maximized on a 4K display, before and after each fix. **`SetProcessDPIAware()` must be called in every such script before `GetWindowRect`/`SetCursorPos`/screenshot calls in the same process invocation** - omitting it silently returns DPI-virtualized coordinates that don't match the real window, which produced two wasted iterations before this was caught.

**Bugs found this way (all confirmed via screenshot, fixed, then re-confirmed via a second screenshot):**

1. **`Forms/Dashboard/DashboardView.Designer.cs` - `lblDashboardTitle` overflowed `pnlTitleBar`.** The label's literal `Size(305, 81)` was taller than its container's literal `Size(2024, 56)` - both hand-typed independently, never cross-checked, never rendered. The title visibly bled into the "Current Organization" row below. Fixed by making the row `Absolute 110F` (generous headroom) and the label `Dock=Left` with `TextOptions.VAlignment=Center` instead of a manually-positioned `Location`/`Size`, so it can never mismatch its container again regardless of DPI or font metrics. Also fixed in passing: `prgLoading`'s literal `X=2848` was outside its 2024px-wide parent entirely - the progress bar was permanently invisible, off to the right.
2. **Same file - `btnRefresh`/`btnViewNotifications` text clipped** ("Refresh" rendered as "Retresh", "View All Notifications" as "w All Notificatio..."). The buttons' literal `Size(100, 30)`/`Size(190, 30)` were narrower than this skin actually renders that caption text. Fixed with `AutoSize = true` + `MinimumSize` (the `DesktopStyle` constant as a floor, not a fixed value).
3. **`Forms/Identity/LoginForm.Designer.cs` - the core bug, three layered issues in the same root cause.** Every `tlpForm` row was `Absolute` (24F for captions, 44F for inputs) - literal guesses against a canvas that was never rendered. In the running app, this DevExpress skin's real per-field height is ~66-70px, not 44px: every `TextEdit`/`ComboBoxEdit` overflowed downward past its own row and painted over the caption in the row immediately below, live-erasing `lblPassword`, `lblPin`, and `lblTheme` entirely and bleeding `chkRememberMe` into `lblLanguage`. (Ruling this down to the actual mechanism took several iterations: DPI was checked and confirmed 100%; `UseSystemPasswordChar`'s documented deferred-handle-recreation quirk was suspected and disproven by temporarily removing it and reproducing the same bug; a pixel-column scan of an actual screenshot - `Bitmap.GetPixel` in a tight loop - was what actually located the missing-text bands precisely enough to see the pattern.) Fixed by converting every non-spacer row from `Absolute` to `AutoSize`, which asks each `Dock=Fill` control for its own real `GetPreferredSize` instead of a guessed literal - this is the only way to be correct across skins without hand-verifying pixel math per skin. Once rows reported their true (larger) heights, the form's old fixed `ClientSize(900,600)`/`MinimumSize(640,480)` were themselves too small and had to grow to `900x900`/`640x700` to avoid clipping the now-correctly-sized content.
4. **Same file - the "Clovent Business Operating System" tagline overlapped the "CBOS" logo, then (after that fix) clipped off the branding panel's right edge.** `lblLogo`/`lblTagline` used the same guessed-`Absolute`-row pattern as `tlpForm` (fixed at #3) - converted to `AutoSize` rows the same way. The tagline text itself was then still too wide for the 320px branding panel at one line; `DevExpress.Utils.WordWrap` on `LabelControl` did not visibly wrap it (tried and confirmed ineffective via screenshot), so the fix uses an explicit `\n` line break in the text instead of relying on automatic wrapping.
5. **`Forms/Identity/Users/UsersForm.Designer.cs`, `RolesForm.Designer.cs`, `Forms/Catalog/Products/ProductsForm.Designer.cs` - every toolbar button clipped** ("New Edit Activate Deactivate Set Password Unlock Refresh" rendered as fragments like "eactiva", "et Passw", "Jnloc", "efres"). Root cause: `DesktopStyle.ButtonWidthSmall/Medium/Large` (80/100/130px) are themselves too narrow for this skin's real button chrome - the same skin-vs-hand-guessed-pixel mismatch as bug #2, but systemic across all three forms since they share the constants. Fixed the same way: every `btnXxx.Size = new Size(DesktopStyle.ButtonWidthX, ...)` became `AutoSize = true` + `MinimumSize = new Size(DesktopStyle.ButtonWidthX, ...)` across all three files (10 buttons total) - the constants now describe a floor, never a ceiling.
6. **`MasterData/MasterDataEditFormBase.cs` - the shared `AddField`-based edit-dialog chrome, used by ~27 `*EditForm`/`*CreateForm` dialogs across every module, silently clipped any dialog with enough fields.** This is the one session 2 explicitly certified as compliant. `Width = 480; Height = 360;` are set once in the base constructor, **before** any subclass's `AddField` calls run (those happen later, in the subclass's own constructor) - so the dialog's size has no relationship to how many fields it actually ends up holding, and `FormBorderStyle.FixedDialog` means the user can't resize around it. `ProductEditForm` (8 fields) was the confirmed live repro: its `_okButton`/`_cancelButton` panel rendered on top of the "Group:" field. Fixed by subscribing a `Load` handler in the base constructor (fires once, after every subclass's `AddField` calls have already happened) that recomputes `ClientSize` from `_contentPanel`'s real preferred size, only ever growing, never shrinking, the fixed `480x360` - this fixes every subclass at once with no per-dialog changes needed. A related width bug in the same class: `AddField` gave every editor a flat `Width = 260`, which is right for a `TextEdit`/`ComboBoxEdit` but was never enough for a `CheckEdit`'s own caption (`"Tax-inclusive pricing"` clipped to `"Tax-inclusive pric"`) - fixed by measuring the checkbox's actual caption via `TextRenderer.MeasureText` instead of reusing the generic 260px guess, with the dialog-width recompute above extended to also grow width (not just height) when a wide `CheckEdit` needs more room than the label column + 260px leaves.

**The pattern underlying every one of these:** a literal pixel `Size`/`Location`/`Width`/`Height` that was hand-typed to *look* plausible but never checked against either (a) the container/sibling it has to coexist with, or (b) how this specific DevExpress skin actually renders that control's chrome and font metrics. Section 1's "no hardcoded pixel positioning" rule was necessary but not sufficient - it catches a control with no `Dock`/`Anchor` at all, but not a `Dock=Fill` control whose own guessed `Size` is simply wrong. **The durable fix in every case above was the same: stop guessing a pixel number for anything that holds text, and let `AutoSize`/`MinimumSize`/`GetPreferredSize` ask the real control for its real size instead.** Future screens should default to this rather than picking a `DesktopStyle`-adjacent literal and hoping it's big enough.

## 8b. Session 4: UX density/redesign pass (left command panel, Dashboard density, systemic fixes)

Session 3 fixed real overlap/clipping bugs but left the app functionally identical to before - same toolbar-above-grid layout, same Dashboard spacing. The user's next request was an explicit UX redesign, not a bug fix: denser Dashboard, and a left command-panel + grid layout for every master-data screen (search/filters/actions/context on the left, grid gets the majority of the width), verified responsive at 1280x720 through 2560x1440. This section records what changed and, as important, what was found and fixed along the way - several of the same DevExpress-skin surprises from Section 8a recurred in new contexts.

**Architectural changes:**

1. **`Forms/Base/CommandPanelLayout.cs` (new)** - the shared left-command-panel-+-grid shell (Section 4's new standard), used by `UsersForm`/`RolesForm`/`ProductsForm`. `MasterData/MasterDataListView.cs` got the identical shape applied inline rather than migrated to this helper (it was verified working first; not worth the regression risk of touching it again to deduplicate). `CommandPanelLayout.Build(host, content)` returns a `FlowLayoutPanel` the caller populates with `BuildSectionHeading("Search"/"Actions"/"Info")` + controls, via `AddCommandButton` for buttons.
2. **`BaseForm.UpdateToolbarPanelSize`** - `ToolbarPanel` now collapses to `Height=0`/`Visible=false` when `ToolbarFlow` has no children (every screen now using `CommandPanelLayout` instead of the toolbar), instead of permanently reserving space for a toolbar band the screen never draws into. Wired from both `ToolbarFlow.SizeChanged` (screens that do use the toolbar) and this control's own `Load` event (screens that never populate it at all, which never fires a `SizeChanged`) - see the class's own comment for why both are needed.
3. **Dashboard density**: the empty-`ToolbarPanel` fix above was the single biggest win (removed a large dead band above the title that had nothing to do with Dashboard's own layout at all - it was `BaseForm`'s inherited, unused toolbar). `pnlTitleBar`/`tlpContext`/`tlpKpi` got 8px bottom `Margin`s for section separation. A KPI-row density trim (`366F` → `300F`/`348F`) was tried and reverted after live screenshots showed it clipping the bottom of decimal values ("50.00", "0.00") under this skin's real 20pt `CardValueFont` rendering - kept at the original, verified-safe `366F`.

**Real bugs found this pass (all confirmed via live screenshot/crash, fixed, then re-confirmed):**

1. **`SplitContainer.SplitterDistance` crash on first navigation to any `MasterDataListView`-based screen** - `ArgumentOutOfRangeException: SplitterDistance must be between Panel1MinSize and Width - Panel2MinSize`, shown via the app's own unhandled-exception dialog. Setting `SplitterDistance` synchronously in the constructor throws because the control is still width-0 (nothing has sized it yet). Tried fixing with a `Load` handler - still crashed, because `Load` isn't a late-enough signal either (DevExpress's `TabbedView` can create the document before finishing its own layout pass). The exception was also confirmed coming from **inside `SplitContainer`'s own internal layout code**, not just this class's explicit assignment - a `try/catch` around the local `SplitterDistance = ...` line alone did not fully guard it. The actual fix: (a) retry from `split.Resize` as well as `Load`, guarded to run only once a valid width is available and only once ever; (b) reduce `Panel1MinSize`/`Panel2MinSize` from a "meaningful floor" (200/320) to a "can't realistically be violated even mid-layout" floor (40/40) - the real 240px command-panel width still comes from `SplitterDistance`, `Panel1MinSize` is just the hard floor DevExpress's own layout code checks against; (c) keep the `try/catch` too, as a last-resort net for whatever internal path still isn't covered.
2. **DevExpress `LabelControl`'s default `AutoSizeMode` overrides an explicitly-assigned `Height` even when `AutoSize` is never set true** - this is the single most-repeated surprise across sessions 3 and 4 (LoginForm's tagline, then `CommandPanelLayout.BuildSectionHeading`'s "Actions"/"Search" headings). Neither a bare `Height = 32` nor `AutoSize = true` stopped a heading from overlapping the control above it; only `AutoSizeMode = DevExpress.XtraEditors.LabelAutoSizeMode.None` (explicitly, not left at its default) makes an assigned `Height` actually stick. **This is now Section 9's guideline 8 - treat it as a hard rule for any `LabelControl` with an assigned `Size`/`Height`, not a case-by-case debugging exercise.**
3. **A `TextEdit` with an explicit `Height` in a `FlowLayoutPanel` renders taller than declared, overlapping whatever the panel already positioned after it** - `UsersForm`/`RolesForm`/`ProductsForm`'s search boxes used `txtSearch.Size = new Size(w, DesktopStyle.ToolbarControlHeight - 2)`; a live screenshot showed the box's real bottom edge overlapping the "Actions" heading `FlowLayoutPanel` had already placed based on the shorter declared height. `MasterDataListView`'s own search box happened to already avoid this (it only ever set `Width`, never `Height`) - which is why `Organizations` rendered clean while `Users` didn't, despite both allegedly following "the same pattern." Fixed by removing the `Height` component everywhere: set `Width` only, and let the control report its own real size.
4. **`Restaurant/Orders/RestaurantPosView.Designer.cs`'s entire right-hand action panel (Hold/Resume/Complete Order/Void Order/Transfer Table/Add Discount/etc., 16 buttons)** used a fixed `Width = 130, Height = 36` per button - never audited by any previous pass since this screen predates the whole Designer-split effort. Every caption longer than "Hold" truncated inside its own button ("Complete Order" → "nplete Or", "Remove Svc. Charge" → "ve Svc. C"). Fixed with the same `AutoSize = true` + `MinimumSize` swap as everywhere else, 16 buttons at once via a single scripted find-replace (`Width = 130, Height = 36` → `AutoSize = true, MinimumSize = new Size(130, 36)`) since every declaration used identical literals. A related header-label wrap bug in the same file (`"Adjustments"` wrapping to `"Adjustment"/"s"`) was `AutoSizeMode.Vertical` (height-only autosize, keeping a fixed width sized for the shorter "Order"/"Table"/"Notes" captions) - changed to `AutoSizeMode.Default` (both dimensions).

**Responsiveness findings (1280x720 through 2560x1440, at this environment's 100% system DPI - see Section 8a for why other DPI values were not physically tested):**

- **1600x900 and above**: every redesigned screen (Dashboard, `MasterDataListView`-based screens, Users/Roles/Products, Restaurant POS) renders cleanly with no overlap, clipping, or hidden controls.
- **1280x720 and 1366x768**: this is a **Ribbon height limitation, not a per-screen layout bug**. The Ribbon's "Session" group (Recent Companies + Recent Branches, stacked) and "Appearance" group (Theme + Language, stacked) make it inherently tall by DevExpress's own content-driven sizing - confirmed the ribbon+tab chrome alone consumes most of a 720-768px-tall window, before any screen's own content is even considered, and this is identical across every screen (Dashboard's content, Restaurant POS's content, and the command panel all hit the same ceiling). At the smallest supported resolution, Dashboard's `tlpMain.MinimumSize` (Section 8b's density comment) keeps it from corrupting/reordering - it clips gracefully behind `scrollHost`'s `AutoScroll`, though the scrollbar itself was not confirmed reachable in every case; `MasterDataListView`'s/`CommandPanelLayout`'s command panel (a `FlowLayoutPanel`, not a `TableLayoutPanel`-in-`Panel`) does reliably scroll, confirmed via a visible working scrollbar at 1920x1080 with the Organizations screen. **This was not fixed at the Ribbon level**: doing so would mean restructuring the Ribbon's own group content (a bigger, cross-cutting change touching `MainForm.Designer.cs`'s ~30 navigation buttons) rather than a contained per-screen fix, and the Ribbon's own built-in collapse control (the chevron already visible in the UI, one click) is a legitimate, standard escape hatch for genuinely small windows - the same pattern real Ribbon-based applications (Office, Visual Studio) rely on. Documented here as a known, deliberate trade-off rather than silently left unaddressed.

## 9. Future UI development guidelines

1. **Never write `control.Location = new Point(...)` with a default `Anchor`.** If a control needs to move/resize with its container, it belongs in a `Dock`ed region, a `TableLayoutPanel` cell, or a `FlowLayoutPanel`, or it needs an explicit `Anchor` combination that actually describes the intended resize behavior (`Top|Left|Right` to stretch width, `Top|Right` to track a corner, etc.). `Anchor = None` is not a centering mechanism - it means "don't track any edge."
2. **Reference `DesktopStyle` constants**, don't hand-pick a new button size/gap/font for a new screen - but treat every `ButtonWidth*`/sizing constant as a **`MinimumSize` floor**, not a fixed `Size`, and pair it with `AutoSize = true` on the control. Session 3 (Section 8a) found these exact constants too narrow for the app's active DevExpress skin, clipping button text ("Refresh" → "Retresh") across three screens - a fixed `Size` can be wrong for a skin nobody hand-verified against; `AutoSize` + a floor cannot be, by construction.
3. **New `BaseForm` screens get `ToolbarFlow` for free** - add buttons to it, in order, with an explicit `Size` and a `Margin`; never add directly to `ToolbarPanel`.
4. **New multi-column card/summary layouts follow Dashboard's `tlpKpi` shape**: a `TableLayoutPanel` with `Percent` columns and either `Percent` or `Absolute` rows (never `AutoSize` rows containing `Dock=Fill` cards - that's a circular measurement WinForms can't resolve; give the *row* an explicit size instead).
5. **Never set `AutoScaleMode`/`AutoScaleDimensions` on any Desktop screen.** This looks like harmless genuine-VS-Designer-parity boilerplate, but combining WinForms' classic Font-based AutoScale with this app's `ApplicationHighDpiMode=PerMonitorV2` makes the Designer recompute and *permanently persist* a rescaled version of every literal coordinate in the file the moment it's opened on a display running at a different scale than whatever baseline was captured - confirmed on a 250% display, where it silently turned a 110px KPI card into a 1px sliver and a 44px toolbar into 1400+px. `ApplicationHighDpiMode=PerMonitorV2` (already declared in the csproj) plus DevExpress's own native per-monitor-DPI control rendering is sufficient on its own - do not add these properties anywhere.
6. **Multiple controls sharing the exact same `Dock` value inside one container is the only real ordering ambiguity in WinForms docking** - the control added first (lowest index in `Controls`) ends up outermost on that edge. Avoid the ambiguity entirely where possible by giving each "row" its own `TableLayoutPanel` row/`FlowLayoutPanel` slot instead of stacking same-`Dock` siblings directly.
7. **No business logic changes ride along with a layout fix.** Every fix in this pass kept field names, constructor signatures, and method bodies identical to their pre-fix state - only where a control is declared/positioned changed. Keep that separation on future layout work too.
8. **A literal `Size`/`Height`/`Width` on any control that holds text (a label, a button, a caption, an edit box) is a guess, not a fact, until it has actually been rendered.** Guideline 4's `Absolute` row exception is for containers (KPI cards, toolbar bands) sized as a deliberate layout decision - it is not license to hand-type a pixel number for a text-bearing control and assume it will fit. Prefer `AutoSize = true` (+ `MinimumSize` where a floor matters) for anything whose content is text, so the control reports its own real size instead of a guess that can be wrong for the active skin, font, or DPI. Section 8a's entire bug list was exactly this mistake, repeated independently across five unrelated files by whoever last touched each one without ever running the app.
9. **Static Designer.cs review is not verification.** Confirming a control has `Dock`/`Anchor`/`TableLayoutPanel` and no bare `Location` (Section 1's rule) catches one specific bug pattern; it does not catch a `Dock=Fill` control whose own `Size` is simply too small for what it holds, which was invisible from source in every Section 8a case. Before calling a layout fix done, launch the app and look at the actual screen - see the session 3 transcript for a scriptable way to do this headlessly (PowerShell + `user32`/`gdi32` P/Invoke to screenshot a specific window), including the `SetProcessDPIAware()` gotcha that silently produces wrong coordinates if skipped.
10. **Any `DevExpress.XtraEditors.LabelControl` given an explicit `Size`/`Height` must also get `AutoSizeMode = LabelAutoSizeMode.None`, explicitly.** `LabelControl`'s default `AutoSizeMode` recomputes and overrides an assigned `Height` regardless of whether `AutoSize` is ever set - this hit three separate labels across sessions 3 and 4 (LoginForm's tagline, `CommandPanelLayout`'s "Actions"/"Search" headings) before being recognized as a general rule rather than three unrelated bugs. If the label should size to its text instead, use `AutoSizeMode.Default` (both dimensions) - `AutoSizeMode.Vertical` alone keeps whatever fixed *width* the control started with, which clipped/wrapped `RestaurantPosView`'s "Adjustments" header (Section 8b) even though its height was correctly automatic.
11. **A `TextEdit`/`ComboBoxEdit`/other `BaseEdit` given an explicit `Height` inside a `FlowLayoutPanel` can render taller than declared and overlap whatever the panel already positioned after it** - the same DevExpress-skin-renders-larger-than-declared pattern as Section 8a's `TableLayoutPanel` rows, but here it isn't caught by row `Absolute` sizing (there is none in a `FlowLayoutPanel`) and instead silently overlaps a *sibling*, not itself. Set `Width` only on these controls when they live in a `FlowLayoutPanel`; leave `Height` unset so the control reports its own real size to the panel doing the positioning.
12. **A `.Designer.cs` file that Visual Studio must open in the Designer can only use the C# subset its CodeDom parser understands** - no `var`, no target-typed `new()`, no object/collection initializers, no generic method invocations (`Enum.GetNames<T>()`), no lambdas, no loops, and no helper methods called from `InitializeComponent()`. The Designer *parses* the file before it instantiates anything, so this is a separate failure mode from ADR-003's DI/constructor guarding, and following ADR-003 alone does not prevent it. On hitting an unsupported construct the Designer aborts with *"The designer cannot process the code at line N"* and everything after that point is simply missing from the surface - which presents as "the form renders only one control even though the Properties window lists many", a parse truncation that looks convincingly like a layout bug. Note the inverse trap too: writing a Designer file in this restricted subset does **not** by itself make it Designer-*correct*, only Designer-*parseable* (guideline 9 still applies). Views whose layout is genuinely composed in code - shared builders like `CommandPanelLayout.Build`, `foreach` over button sets, lambda handlers - should not be contorted into the subset; mark them `[System.ComponentModel.DesignerCategory("Code")]` so VS opens them as code and never attempts a Designer load. See [ADR-007](adr/ADR-007-Designer-CodeDom-Constraints.md) for the audit and the current category split.
13. **When wiring a `SplitContainer`, never set `SplitterDistance` synchronously in a constructor, and don't assume a `try/catch` around your own assignment is a complete guard.** The control is width-0 until its host has actually laid it out, and `SplitContainer` enforces `Panel1MinSize <= SplitterDistance <= Width - Panel2MinSize` from its *own* internal layout code on every resize - not just when application code sets `SplitterDistance` - so a transient width during a document's own creation can throw an uncatchable-by-you `ArgumentOutOfRangeException` straight through WinForms' message loop. Keep `Panel1MinSize`/`Panel2MinSize` small (Section 8b used 40/40) so the constraint can't realistically be violated even mid-layout, and set the real desired width via `SplitterDistance` from a guarded, retry-on-`Resize` handler (see `Forms/Base/CommandPanelLayout.Build`) rather than a fixed floor that's actually meant to be the real layout width.
