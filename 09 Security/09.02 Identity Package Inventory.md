# 09.02 Identity Package Inventory

## Purpose

Documents every NuGet package that touches Identity/Authentication in this repository as of the Repository Stabilization pass: why it was added, which architectural layer it belongs to, and whether it introduces coupling that the Solution Architect should be aware of before Authentication is implemented.

Two projects currently carry Identity-related packages:

- `src/Clovent.Authentication` — the product Authentication module (empty scaffold; package references only, no implementation yet)
- `Tools/Clovent.CLI/src/Clovent.Modules.Identity` — an internal proof-of-concept Identity module (has real EF Core entities and a stub login; not part of the product)

This document does not decide anything — it records facts so the next architectural specification can be made with full visibility into what's already referenced.

---

## `src/Clovent.Authentication`

### Microsoft.Extensions.Identity.Core (10.0.10)

- **Why it exists:** Replaces `Microsoft.AspNetCore.Identity 2.3.11` (removed during stabilization — that package was the last version ever published, abandoned since ASP.NET Core 3.0, and pulled a transitively vulnerable dependency, `System.Security.Cryptography.Xml`, with 7 open high-severity advisories). Provides the core Identity abstractions: `IdentityUser`, `IdentityRole`, `UserManager<TUser>`, `RoleManager<TRole>`, `IPasswordHasher<TUser>`, password/lockout/two-factor option types — with no ASP.NET Core HTTP-hosting dependency.
- **Infrastructure-only?** **No.** `IdentityUser`/`UserManager<TUser>` are typically consumed directly by Application (and sometimes Domain) code, not hidden behind an Infrastructure boundary. Treat this as an Application-layer dependency at minimum.
- **Architectural coupling — significant, needs an explicit decision:** If `User` (the domain entity) is made to inherit `IdentityUser<TKey>`, the Domain layer becomes coupled to a Microsoft framework base class — this conflicts with the documented DDD standard (`07 Domain Driven Design`: entities/aggregates should extend `AggregateRoot<TId>` with strongly-typed IDs, not a third-party base class). The alternative — keep `User` as a plain `AggregateRoot<UserId>` and use `UserManager<TUser>` only in the Infrastructure layer as an implementation detail behind a first-party interface — avoids the coupling but forgoes some of Identity.Core's built-in convenience (password/lockout policy enforcement, security stamps, etc., would need to be re-implemented or wrapped). **This is the same open question already raised in the Technical Assessment Report (Section 12, Q6) and is not resolved by this stabilization pass.**

### Microsoft.Extensions.Identity.Stores (10.0.10)

- **Why it exists:** Provides the storage-abstraction interfaces (`IUserStore<TUser>`, `IRoleStore<TRole>`, and related marker interfaces) that `UserManager`/`RoleManager` need to persist through. On its own it does nothing — it exists to be implemented, most commonly via `Microsoft.AspNetCore.Identity.EntityFrameworkCore` (**not currently referenced anywhere in this repository**).
- **Infrastructure-only?** **Mostly yes** — the store implementation belongs in Infrastructure/Persistence. The interfaces themselves may need to be visible from the Application layer for DI registration.
- **Architectural coupling:** Commits to ASP.NET Core Identity's "store" pattern for persistence. `src/Clovent.Authentication` already scaffolds a parallel, framework-agnostic option (`Repositories/Interfaces/IUserRepository.cs`, `Users/Repositories/IUserRepository.cs`, etc. — empty placeholders, not implemented). **These two approaches are redundant with each other** — the architect should pick one persistence pattern for Identity (Identity.Stores vs. a custom repository), not carry both forward into implementation.

### Microsoft.EntityFrameworkCore (10.0.10)

- **Why it exists:** ORM/persistence for Identity data.
- **Infrastructure-only?** Yes.
- **Architectural coupling:** None beyond what's already documented — EF Core is the platform's stated persistence technology (`05 Software Architecture`). Consistent, not a new commitment.

### Microsoft.Extensions.DependencyInjection (10.0.10)

- **Why it exists:** DI container abstractions, for the (currently empty) `Extensions/ServiceCollectionExtensions.cs` composition root.
- **Infrastructure-only?** No — DI registration is a cross-cutting/composition-root concern, not tied to one layer.
- **Architectural coupling:** None — the standard .NET DI abstraction, already the platform-wide choice everywhere else in the repository.

## `Tools/Clovent.CLI/src/Clovent.Modules.Identity`

*(Internal proof-of-concept module — not part of the product solution. Included here because it is the only place in the repository with a working Identity persistence model, and its package choices are informative for the product design.)*

### BCrypt.Net-Next (4.2.0)

- **Why it exists:** Password hashing, used by the module's `PasswordHasher : IPasswordHasher`.
- **Infrastructure-only?** Yes — implements a security primitive behind a first-party interface.
- **Architectural coupling:** Low in isolation (narrow, swappable library) — **but it directly overlaps with `Microsoft.Extensions.Identity.Core`'s built-in `IPasswordHasher<TUser>`** (item above, in `src/Clovent.Authentication`), which ships its own PBKDF2-based hasher. If Identity.Core is adopted as the framework for the product module, this is a concrete decision point: either use Identity.Core's built-in hasher, or keep BCrypt via a custom `IPasswordHasher<TUser>` implementation — not both without a reason.

### MediatR (12.4.1)

- **Why it exists:** CQRS mediator, per the documented standard (`06 Coding Standards`: "CQRS: Commands for write operations, Queries for read operations handled via MediatR handlers"). **Not currently used anywhere in this module** — `LoginRequest`/`LoginResponse` are called directly, not via `IRequest`/`IRequestHandler`.
- **Infrastructure-only?** No — Application-layer concern.
- **Architectural coupling:** This is the intended, already-documented pattern, not an unplanned coupling. Currently dead weight until Application-layer command/query classes are actually written for Identity.

### Microsoft.EntityFrameworkCore.SqlServer (10.0.10)

- **Why it exists:** SQL Server provider for `IdentityDbContext`.
- **Infrastructure-only?** Yes.
- **Architectural coupling:** Commits specifically to SQL Server as the backing engine. Reasonable for an enterprise on-prem/SaaS target, but should be confirmed as the platform-wide database engine for all future modules, not assumed from Identity alone.

### Microsoft.EntityFrameworkCore.Design / Microsoft.EntityFrameworkCore.Tools (10.0.10, both `PrivateAssets="all"`)

- **Why it exists:** Enables `dotnet ef migrations add` / `database update` tooling.
- **Infrastructure-only?** Yes — and further, **build/tooling-time only**; `PrivateAssets="all"` correctly prevents either from flowing into anything that references this project.
- **Architectural coupling:** None.

### Microsoft.Extensions.Configuration / .Json / .EnvironmentVariables (10.0.10)

- **Why it exists:** Added during this stabilization pass so `DesignTimeDbContextFactory` reads its SQL Server connection string from `appsettings.json`/environment variables instead of a hardcoded developer machine name.
- **Infrastructure-only?** Yes — design-time tooling concern only.
- **Architectural coupling:** None — standard framework configuration abstraction, already used elsewhere in the repository (`Clovent.CLI`, `Clovent.CBOS.Desktop`).

## `Tools/Clovent.CLI/src/Clovent.Shared` (foundation used by all modules, including Identity)

### MediatR.Contracts (2.0.1)

- **Why it exists:** Supplies `INotification`, which `IDomainEvent` extends (`Domain/DomainPrimitives.cs`): `public interface IDomainEvent : INotification`.
- **Infrastructure-only?** No — this is a **Domain-layer** dependency (`IDomainEvent` is a Domain primitive, used by every module's aggregates, including Identity's).
- **Architectural coupling — worth the architect's explicit sign-off:** Strict Clean Architecture conventionally keeps the Domain layer free of third-party package dependencies. `MediatR.Contracts` is unusually minimal and stable (it exists specifically to be a dependency-free marker-interface package, distinct from the full `MediatR` package), which makes this a low-risk, common choice — but it is still a third-party coupling baked into the Domain layer of **every** module, not just Identity, since `AggregateRoot<TId>`/`IDomainEvent` are shared foundation types. Recommend the architect explicitly ratify this (or replace `IDomainEvent : INotification` with a first-party marker interface plus a MediatR-specific adapter at the Application layer) before more modules are built on top of it.

## Not yet referenced, but implied by the above

- **`Microsoft.AspNetCore.Identity.EntityFrameworkCore`** — the standard EF-Core-backed store implementation for `Microsoft.Extensions.Identity.Stores`. Not added in this pass (would be a design commitment, not a stabilization fix). Needed only if the architect confirms the Identity.Stores + EF Core path over the custom repository scaffolding already present in `src/Clovent.Authentication`.
